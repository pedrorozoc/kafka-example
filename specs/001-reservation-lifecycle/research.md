# Decisiones de diseño

El cambio de disponibilidad (FR-005 y FR-008) se apoya en la representación de `reservationTime` y el protocolo transaccional existentes. FR-014 requiere preservar las reservas registradas.

| Decisión | Fundamento | Alternativa considerada |
| --- | --- | --- |
| Java 25, Spring Boot 4.2.0 y Maven Wrapper 3.9.x | Spring MVC, Data JPA y Bean Validation cubren las capas y contratos de la constitución. El BOM de Boot coordina las dependencias. MapStruct 1.6.3 y su procesador de igual versión generan mappers con el modelo de componentes de Spring. | Gradle también es compatible. Se elige un único sistema de construcción reproducible. |
| Mantener cuatro capas por módulo y consumir `TableCatalog` desde `reservations.service` | Los principios I, II y VI de la constitución 1.3.0 sitúan el contrato público en `tables.service`. La implementación `DatabaseTableCatalog` tiene visibilidad de paquete y encapsula el acceso a persistencia y los bloqueos de PostgreSQL. | Una dependencia directa al servicio concreto expondría al consumidor a un mecanismo de persistencia volátil. |
| Conservar la validación de `partySize` entre 1 y 12 en el DTO de creación | `@Valid @RequestBody` activa la restricción `@Max(12)` existente antes de consultar disponibilidad. Aplica FR-013. | Validar en el servicio trasladaría una regla de entrada a la capa de negocio. |
| Mantener `BigInteger` y la columna `numeric` para los registros persistidos | El límite rige las nuevas solicitudes HTTP. Una reserva anterior de más de 12 comensales conserva su código, estado y asignación y sigue siendo consultable. | Un límite retroactivo en el esquema podría invalidar registros existentes. Cambiar una migración ya aplicada afectaría a la validación de Flyway. |
| PostgreSQL 17, migraciones Flyway y PostgreSQL real en pruebas con Testcontainers o una base de pruebas configurada | La verificación de exclusión entre solicitudes depende de la semántica de transacciones del motor que ejecuta el servicio. Una prueba HTTP enfocada que instrumente el punto de entrada al servicio permite observar que 13 no llega a la lógica de disponibilidad. | Verificar solo las filas persistidas confirma que 13 no se guarda, pero no permite determinar si se consultó el catálogo. |
| Bloquear las mesas candidatas en orden de ID y consultar sus asignaciones en una sentencia posterior bajo READ COMMITTED | La consulta posterior incorpora los commits producidos durante la espera. El bloqueo dura hasta que termina la transacción. También puede haber espera entre instantes distintos para una misma mesa. | Consultar antes de bloquear permite una doble asignación. Saltar filas bloqueadas puede rechazar una solicitud para un instante libre. |
| Comparar por igualdad el par canónico `reservation_time` y `reservation_time_remainder` de las reservas confirmadas | El lector actual normaliza a UTC, conserva los microsegundos y guarda los dígitos adicionales sin ceros finales. Se detectan desplazamientos equivalentes y se distinguen fracciones válidas dentro del mismo microsegundo. | Comparar solo el `timestamptz` confunde instantes submicrosegundo. Comparar las cadenas recibidas separa representaciones equivalentes. |
| Reutilizar las columnas, las migraciones aplicadas y el índice parcial por mesa y `reservation_time` | El índice puede acotar la consulta por mesa candidata y microsegundo, con el resto decimal como filtro. El cambio queda en el servicio y su consulta. Los datos existentes, incluido el resto vacío por defecto, siguen siendo válidos. | Un índice único solo por mesa y microsegundo impediría confirmaciones válidas. Incluir un texto de longitud variable como clave B-tree añade límites de tamaño y una migración innecesaria para el protocolo de asignación actual. |
| Actualizar conjuntamente las instancias que crean reservas si comparten base | Ambas versiones pueden consultar el mismo esquema, pero durante una actualización mixta la versión anterior puede rechazar por su regla de duración. Un cambio coordinado de los escritores aplica una sola regla de disponibilidad. | Un despliegue con escritores de ambas versiones mezcla reglas de negocio para solicitudes equivalentes. |
| Código público UUID aleatorio, respuesta 201 con Location para ambos resultados finales | Cada solicitud válida crea una reserva consultable, incluso cuando el restaurante carece de una mesa apta. GET requiere únicamente el código y devuelve el estado. | Responder con un error por falta de mesa perdería la distinción entre rechazo de negocio y error de entrada. |
| ProblemDetail para errores, con título y detalle en español | El advice global aplica el contrato de la constitución también a JSON ilegible y a fallos de conversión. | Respuestas de error diferentes por controlador obligarían al cliente a interpretar varios formatos. |
