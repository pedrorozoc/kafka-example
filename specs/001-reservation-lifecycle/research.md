# Decisiones de diseño

El backend ya implementa el ciclo de reserva. La revisión de FR-013 se apoya en el DTO, el controlador y las pruebas HTTP existentes.

| Decisión | Fundamento | Alternativa considerada |
| --- | --- | --- |
| Java 25, Spring Boot 4.2.0 y Maven Wrapper 3.9.x | Spring MVC, Data JPA y Bean Validation cubren las capas y contratos de la constitución. El BOM de Boot coordina las dependencias. MapStruct 1.6.3 y su procesador de igual versión generan mappers con el modelo de componentes de Spring. | Gradle también es compatible. Se elige un único sistema de construcción reproducible. |
| Mantener cuatro capas por módulo y consumir `TableCatalog` desde `reservations.service` | Los principios I, II y VI de la constitución 1.3.0 sitúan el contrato público en `tables.service`. La implementación `DatabaseTableCatalog` tiene visibilidad de paquete y encapsula el acceso a persistencia y los bloqueos de PostgreSQL. | Una dependencia directa al servicio concreto expondría al consumidor a un mecanismo de persistencia volátil. |
| Validar `partySize` entre 1 y 12 inclusive en el DTO de creación | FR-013 prevalece sobre el supuesto anterior de validación mínima de la especificación. Jakarta Validation admite `@Max(12)` sobre `BigInteger`. Con `@Valid @RequestBody`, Spring MVC aplica el límite antes de llamar al controlador y el advice existente devuelve 400 con el mensaje de la restricción en español. | Validar en el servicio trasladaría una regla de entrada a la capa de negocio. Acotar el tipo Java o introducir la regla en el deserializador mezclaría el valor máximo con las reglas de lectura JSON. |
| Mantener `BigInteger` y la columna `numeric` para los registros persistidos | El límite rige las nuevas solicitudes HTTP. Una reserva anterior de más de 12 comensales conserva su código, estado y asignación y sigue siendo consultable. | Un límite retroactivo en el esquema podría invalidar registros existentes. Cambiar una migración ya aplicada afectaría a la validación de Flyway. |
| PostgreSQL 17, migraciones Flyway y PostgreSQL real en pruebas con Testcontainers o una base de pruebas configurada | La verificación de exclusión entre solicitudes depende de la semántica de transacciones del motor que ejecuta el servicio. Una prueba HTTP enfocada que instrumente el punto de entrada al servicio permite observar que 13 no llega a la lógica de disponibilidad. | Verificar solo las filas persistidas confirma que 13 no se guarda, pero no permite determinar si se consultó el catálogo. |
| Bloquear las mesas candidatas en orden de ID, luego consultar las ocupaciones en una sentencia distinta bajo READ COMMITTED | El bloqueo dura hasta el commit. La consulta posterior ve las reservas confirmadas durante la espera. Bloquear varias candidatas simplifica la decisión para el catálogo de un único restaurante, a costa de hacer esperar incluso a solicitudes de franjas distintas. | Consultar disponibilidad antes de bloquear permite una doble asignación. Saltar filas bloqueadas puede rechazar una solicitud para una franja libre. |
| Recibir fecha y hora con desplazamiento UTC explícito y comparar instantes | Dos representaciones del mismo instante compiten por la misma mesa. Sumar 90 minutos al instante inicial conserva la duración al cruzar medianoche o cambiar la hora civil. | Una fecha local sin desplazamiento exigiría definir la zona del restaurante y resolver horas locales ambiguas. |
| Código público UUID aleatorio, respuesta 201 con Location para ambos resultados finales | Cada solicitud válida crea una reserva consultable, incluso cuando el restaurante carece de una mesa apta. GET requiere únicamente el código y devuelve el estado. | Responder con un error por falta de mesa perdería la distinción entre rechazo de negocio y error de entrada. |
| ProblemDetail para errores, con título y detalle en español | El advice global aplica el contrato de la constitución también a JSON ilegible y a fallos de conversión. | Respuestas de error diferentes por controlador obligarían al cliente a interpretar varios formatos. |
